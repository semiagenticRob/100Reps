# 100 Reps Dashboard — Field Notes & Lessons

## Context

Robert is executing 100 product launches in parallel. The current `100repsproject.com` dashboard tracks status per-rep but offers **no reflective surface**. He's "juggling balls" without pausing — lessons learned on one rep don't compound into the next. Specific recent example: distribution failures hitting both Rep 011 and Rep 014 with no link between the realizations.

The fix is a **build-in-public reflection journal** layered onto the existing dashboard:

1. **Daily Field Notes** — voice-memo'd reflections, sanitized and formatted by his local Telegram agent into dated markdown entries that auto-publish.
2. **Lessons library** — curated, named insights (e.g., "Distribution beats craft for physical-product reps") that Robert hand-writes when the agent flags a recurring pattern in its Telegram reply. The Lessons surface is the public artifact — a "playbook earned" — distinct from the journal stream.
3. **Vault-style interlinking** — entries and lessons reference reps and tags; the dashboard renders backlinks (per-rep entries, tag pages) so patterns surface visually.

The intended outcome: a forced daily reflection habit, a public artifact people can read and share, and structural compounding so insight from Rep N flows into Rep N+1.

## Scope

In-scope:
- New content types (field-notes/, lessons/) at repo root with markdown source-of-truth
- Telegram-driven authoring pipeline (extension of existing `rep-update` skill)
- Dashboard UI: left-side reading panel for Field Notes; separate Lessons page
- Build step (GH Action) producing JSON manifests consumed by client-side dashboard
- Privacy sanitization (same rules as existing `next_step`/`blocker` public fields)

Out-of-scope:
- Auth/private surfaces (everything is public)
- Replacing the private Obsidian vault; this is a separate public artifact
- Tag pages, graph view, or full-text search (deferred until volume justifies)

## Architecture

### File layout (additions to existing repo)

```
field-notes/

  2026-04-25.md
  ...
lessons/
  distribution-beats-craft.md
  formspree-spam-default.md
  ...
docs/

  lessons.json            # generated by build step
.github/workflows/

  build-journal.yml       # NEW — generates field-notes.json + lessons.json
scripts/
```

### Frontmatter schemas

**Field note (`field-notes/YYYY-MM-DD.md`):**
```yaml
---
date: 2026-04-26
reps: [11, 14]
tags: [distribution, cold-outreach]
mood: stuck       # optional, free-form one-word
---
Body markdown. Voice-memo content cleaned up by the agent.
Wikilinks like [[lesson:distribution-beats-craft]] are rendered as links.
```

**Lesson (`lessons/<slug>.md`):**
```yaml
---
slug: distribution-beats-craft
title: Distribution Beats Craft for Physical-Product Reps
reps: [9, 11, 14]
tags: [distribution]
first_seen: 2026-03-12
last_updated: 2026-04-26
---
The lesson body. Markdown. May reference [[rep:011]] or other lessons.
```

Every file under `lessons/` is published. There is no `status` field and no `_pending/` directory — Robert is the only author of lesson files. The agent never writes to `lessons/`; it only suggests new lessons in its Telegram reply, and Robert decides whether to hand-create the file.

### Authoring pipeline

Extends the existing local Telegram → `rep-update` skill flow. Robert's local agent (Claude Code session triggered by Telegram messages) handles voice memos as follows:

1. Receive voice memo + transcript via Telegram.
2. Sanitize transcript per public-field privacy rules (no names, emails, phone numbers — same sanitizer used for `next_step`/`blocker`).
3. Identify rep references (by name or id) and tags.
4. Write `field-notes/YYYY-MM-DD.md`. If the file already exists for today, **append** the new content to the existing body separated by `---` and a timestamp marker (e.g., `## 2026-04-26 19:42`). Never overwrite. This preserves morning-vs-evening reflection arcs in a single day's entry.
5. Compare against existing lessons. **The agent never writes to `lessons/`.** Robert is the sole author of lesson files. Instead, the agent surfaces in its Telegram reply:
   - Existing lessons that the entry reinforces (with proposed `last_updated` bump, new rep additions to `reps`, and any one-line evidence note worth appending). Robert decides whether to apply.
   - Any *new* lessons the entry suggests (proposed slug, proposed title, one-paragraph rationale, contributing rep ids). Robert decides whether to hand-create `lessons/<slug>.md`.
6. Commit and push the field-note write to `100Reps-dashboard`. The GH Action regenerates `docs/*.json` and the live site updates.
7. Reply to Robert with a summary: entry written (or appended), reps tagged, any lesson reinforcements suggested, any new-lesson suggestions, anything that triggered a sanitization edit.

### Build step

`scripts/build-journal.py` (Python; matches the existing `python3 -c "import yaml..."` validation pattern). Walks `field-notes/` (date-sorted desc) and `lessons/`, reads frontmatter + body, renders body markdown to HTML server-side, and emits two JSON files:

```json
// docs/field-notes.json
{
  "entries": [
    {
      "date": "2026-04-26",
      "reps": [11, 14],
      "tags": ["distribution", "cold-outreach"],
      "html": "<p>Spent the morning...</p>",
      "preview": "Spent the morning reviewing why myvoiceprofile feels stuck..."
    }
  ]
}
```

```json
// docs/lessons.json
{
  "lessons": [
    {
      "slug": "distribution-beats-craft",
      "title": "Distribution Beats Craft for Physical-Product Reps",
      "reps": [9, 11, 14],
      "tags": ["distribution"],
      "first_seen": "2026-03-12",
      "last_updated": "2026-04-26",
      "html": "<p>The lesson body...</p>"
    }
  ]
}
```

GH Action `build-journal.yml` runs on push to main when `field-notes/**` or `lessons/**` changes. It runs the Python script and commits the regenerated JSONs to `docs/`. Mirrors the existing `sync-reps-yaml.yml` pattern.

### Dashboard UI

#### Main page (`docs/index.html`)

Layout becomes a two-column flex container:

```
+-------------------+ +----------------------------------+
| FIELD NOTES (~360)| | DASHBOARD (existing, fills rest) |
| [notes][lessons→] | |                                  |
| <feed>            | | [header / pills / table]         |
+-------------------+ +----------------------------------+
```

- Left panel ~360px wide on `>= 900px` viewports. Always-open by default.
- Has a `[<<]` collapse toggle that minimizes it to a 32px icon rail.
- On `< 900px` viewports, panel collapses to icon rail by default; click expands to a full-screen overlay.
- Panel content:
  - Header: `FIELD NOTES` title, two pill-tabs `[notes]` (active) and `[lessons →]` (links to `/lessons.html` — NOT a tab, it's a navigation link).
  - Body: vertical feed. Newest entry expanded with full body. Older entries show date + rep chips + tags + first-line preview, click to expand inline.
  - Footer: `[archive →]` link to a future full-archive page (out of scope for now — link can be inert until volume warrants it).
- Rep chips like `[011]` are clickable: filters the rep table to that rep. Tags like `#distribution` filter by tag (deferred — for now they're plain text).
- Staleness indicator: if newest entry is > 3 days old, panel header shows a small amber dot — public accountability signal.

The existing rep table, pills, search, sort, and blocker ticker remain unchanged on the right side.

#### Lessons page (`docs/lessons.html`)

New, separate page. Same dark-terminal aesthetic. Single column.

- Each lesson is a card with title, rep chips, first_seen date, expandable body.
- Sort order: most recently updated first.
- Filter pills at top by tag (deferred until > 5 lessons exist).
- Each rep chip on this page links to that rep's row on the main dashboard.

#### Per-rep cross-link (existing dashboard enhancement)

When Robert's existing rep-detail expand on the dashboard opens, the panel below the table grows a "Field Notes" subsection listing entries that referenced this rep. Cheap to implement once `field-notes.json` is loaded — just filter by `reps` field.

### Privacy

All public-facing content (field notes, lessons) follows the existing `next_step`/`blocker` sanitization rules from `REPS_YAML_SPEC.md`:

- No personal names (first + last)
- No email addresses
- No phone numbers
- No private internal references

The agent applies sanitization during step 2 of the authoring pipeline. The `rep-update` skill already implements this — it gets reused, not reinvented.

## Verification

**Local-first.** Nothing gets pushed to `main` until every local check passes. The live dashboard is public.

### Phase A — local validation (before any push)

1. Hand-write `field-notes/2026-04-27.md` with rep refs + tags + body, and `lessons/test-lesson.md`.
2. Run `python3 scripts/build-journal.py` locally. Confirm exit 0, valid `docs/field-notes.json` and `docs/lessons.json`, JSON shape matches schemas above.
3. Validate generated JSON: `python3 -c "import json; json.load(open('docs/field-notes.json')); json.load(open('docs/lessons.json')); print('VALID')"`.
4. Serve dashboard locally: `cd docs && python3 -m http.server 8000`. Confirm left panel renders, rep chips clickable and filter the rep table, `[lessons →]` navigates correctly, existing rep table/pills/search/sort/blocker ticker unchanged.
5. Resize below 900px — confirm panel collapses to icon rail with expand-to-overlay behavior.
6. Sanitization test: transcript with fake email + "John Smith" name through agent in dry-run mode. Confirm sanitizer strips both.
7. Same-day append test: write the entry, run the agent again with new content for the same date, confirm body is appended below `---` + timestamp separator (not overwritten).

### Phase B — staged push

8. Commit and push only after Phase A is fully green. Verify GH Action `build-journal.yml` runs and commits regenerated `docs/*.json` (or is a no-op if local build already produced them).
9. Open `100repsproject.com` live, confirm parity with local: same entry visible, same lesson listed, no rep-table regressions.
10. If anything is wrong on live, revert immediately rather than patching forward.

A `meta.total` integrity check (parallel to the existing `reps.yaml` validator) is not needed for field-notes — they're append-only.
